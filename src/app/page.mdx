## Why Keploy for Go Developers?

If you have built microservices in Go, you already know the pain of testing database and HTTP layers. The traditional testing lifecycle in Go looks something like this:

1. **Tedious Interfaces**: You define Go interfaces for every repository (`type UserRepository interface`), generate mocks using `mockgen` or `testify`, and write verbose table-driven unit tests.
2. **Brittle Unit Mocks**: Unit tests with fake mocks pass cleanly on your laptop, but when your application interacts with a live MongoDB cluster in staging, subtle differences in query operators, wire protocol serialization, or indices cause production outages.
3. **Flaky End-to-End Suites**: Setting up Docker-Compose or Testcontainers in CI is slow, consumes heavy resources, and frequently breaks due to race conditions or leftover state in the database.

<Callout type="aha" title="The Keploy Paradigm Shift">
  Instead of writing manual tests and fake mocks, **Keploy turns real API interactions into automated test cases and wire-level database mocks**. 

  It operates at the network socket layer using Linux **eBPF (Extended Berkeley Packet Filter)**. Your Go application does not need any SDK dependencies, code alterations, or test wrappers.
</Callout>

<section id="architecture">
## Architecture & How eBPF Interception Works

To understand why Keploy is so effective, we must understand what happens under the hood. 

Keploy operates in two distinct phases: **Record Mode** and **Test Mode**. Explore the interactive diagram below to see how traffic flows:

<ArchitectureDiagram />

### 1. In Record Mode (`keploy record`)
When you launch your Go application with Keploy:
- Keploy loads an **eBPF program** into the kernel (or attaches a transparent network proxy in containerized environments).
- As you send HTTP requests (e.g. shortening a URL via `POST /url`), Keploy intercepts the incoming HTTP payload, headers, and status code.
- Simultaneously, when the Go Gin handler executes queries against MongoDB (port `27017`), Keploy captures the exact **MongoDB Wire Protocol** frames (such as `OpMsg` and `OpQuery` requests, along with MongoDB's BSON response).
- Keploy serializes the HTTP interaction into `./keploy/test-set-0/tests/test-1.yaml` and the database interactions into `./keploy/test-set-0/mocks.yaml`.

### 2. In Test / Replay Mode (`keploy test`)
When you run your test suite:
- **MongoDB does not need to run!** You can shut down your database instance completely.
- Keploy's internal test runner replays the recorded HTTP request to `http://localhost:8080/url`.
- When the Go application attempts to connect to `localhost:27017` to write or query data, Keploy intercepts the TCP connection at the socket layer and returns the exact recorded BSON response from `mocks.yaml`.
- The application executes its normal business logic without realizing the database is virtualized.
- Keploy captures the live response and compares it field-by-field against the recorded baseline in `test-1.yaml`.
</section>

### Understanding the Application Code
Let's look at `main.go` and `handler.go`. The URL shortener provides two core endpoints:
- `POST /url`: Accepts a JSON body `{"url": "https://google.com"}`. Generates a shortened hash, persists it in MongoDB with a creation timestamp (`ts`), and returns the short URL.
- `GET /:param`: Looks up the shortened hash in MongoDB and responds with an HTTP `302 Redirect` to the destination URL.

<CodeBlock language="go" filename="handler.go (Excerpt)">
{`type ShortenReq struct {
    URL string \`json:"url"\`
}

type ShortenResp struct {
    Ts  int64  \`json:"ts"\`
    URL string \`json:"url"\`
}

func ShortenURL(c *gin.Context) {
    var req ShortenReq
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(http.StatusBadRequest, gin.H{"error": err.Error()})
        return
    }

    id := generateShortID()
    now := time.Now().UnixNano() // Note: Dynamic runtime timestamp!
    
    // Save mapping into MongoDB collection
    _, err := collection.InsertOne(c.Request.Context(), bson.M{
        "_id": id,
        "url": req.URL,
        "ts":  now,
    })
    ...
}`}
</CodeBlock>

## Step 3: Deep Dive into Generated Tests & Mocks

Let's inspect the files Keploy created in your workspace:

```txt
keploy/
└── test-set-0/
    ├── mocks.yaml
    └── tests/
        ├── test-1.yaml
        └── test-2.yaml
```

### Inspecting `test-1.yaml` (The Ingress Test Contract)
Opening `test-1.yaml`, we find the complete HTTP transaction captured declaratively:

<CodeBlock language="yaml" filename="keploy/test-set-0/tests/test-1.yaml">
{`version: api.keploy.io/v1beta1
kind: Http
name: test-1
spec:
    metadata: {}
    req:
        method: POST
        url: http://localhost:8080/url
        header:
            Content-Type: application/json
        body: |-
            {
              "url": "https://google.com"
            }
    resp:
        status_code: 200
        header:
            Content-Type: application/json; charset=utf-8
        body: '{"ts":1718943885198315028,"url":"http://localhost:8080/Lhr4BWAi"}'
    assertions:
        noise:
            header.Date: []`}
</CodeBlock>

### Inspecting `mocks.yaml` (The Egress Dependency Contract)
This is where Keploy's magic truly shines. Look inside `mocks.yaml`:

<CodeBlock language="yaml" filename="keploy/test-set-0/mocks.yaml (Excerpt)">
{`version: api.keploy.io/v1beta1
kind: Mongo
name: mock-1
spec:
    metadata:
        operation: '{ OpMsg flags: 0, sections: [{ ... update: "url-shortener", updates: [{ _id: "Lhr4BWAi", url: "https://google.com" }] }] }'
    requests:
        - header:
            Opcode: 2013 # OpMsg opcode
          message:
            sections:
                - '{ SectionSingle msg: {"update":"url-shortener","ordered":true,"$db":"keploy"} }'
    responses:
        - header:
            Opcode: 1
          message:
            documents:
                - '{"n":{"$numberInt":"1"},"nModified":{"$numberInt":"1"},"ok":{"$numberDouble":"1.0"}}'`}
</CodeBlock>

<Callout type="aha" title="A-ha! Moment: Wire Protocol Mocks">
  Notice that Keploy did not mock a Go function or interface. It recorded the **actual MongoDB Wire Protocol network packet exchange**! 

  This means you can change your Go Mongo driver version or refactor your internal Go data models—as long as the database protocol remains compatible, your tests will faithfully execute without updating a single mock!
</Callout>
</section>

## Step 4: Replay Tests & The Dynamic Timestamp Gotcha

Now let's test our application. First, prove that MongoDB is no longer needed:

<CodeBlock language="bash" filename="Terminal">
{`# Shut down the MongoDB container completely!
docker stop mongoDb`}
</CodeBlock>

Now execute `keploy test`:

<CodeBlock language="bash" filename="Terminal">
{`keploy test -c "docker run -p 8080:8080 --name ginMongoApp --network keploy-network gin-app:1.0" --delay 10`}
</CodeBlock>

### The First Test Run Result: Test Failed! 🚨

When you run this command for the very first time, Keploy's test suite will fail on `test-1`. 

Why? Let's check the test diff output:

```txt
--------------------------------------------------------------------
  Test Set: "test-set-0"
  Test: "test-1" (POST /url)
--------------------------------------------------------------------
  Result: FAILED ❌
  Diff:
    Field: body.ts
    Expected: 1718943885198315028
    Actual:   1718943921004123891
--------------------------------------------------------------------
```

<Callout type="warning" title="The 'A-ha!' Learning: Understanding Dynamic Noise">
  **Why did the test fail?** 
  
  In `handler.go`, line 38 calls `time.Now().UnixNano()` to generate the creation timestamp. When Keploy replayed the request, the Go app executed that line again, creating a *new* current timestamp. 
  
  Keploy's assertion engine strictly validates the entire response body. It detected that `1718943921004123891` did not match `1718943885198315028` and rightly flagged a mismatch.
</Callout>
</section>

## Step 5: Declarative Noise Filtering & 100% Pass

In real-world applications, APIs frequently contain dynamic, non-deterministic values:
- Timestamps (`created_at`, `ts`, `Date`)
- Random UUIDs (`id: "c82b1...`)
- Authentication tokens & session cookies

Keploy handles this elegantly through **Noise Assertions**.

### Adding `body.ts` to `assertions.noise`
Open `keploy/test-set-0/tests/test-1.yaml` and add `body.ts: []` under the `noise` section:

<section id="devrel-learnings">
## DevRel Insights, Gotchas & Best Practices

As a Developer Relations advocate, guiding engineers through their first Keploy implementation requires anticipating the common friction points and highlighting the "aha!" moments:

### 1. The Power of Zero Code Changes
Developers are often skeptical when told a tool provides automated integration testing. They expect a heavy SDK, custom context wrappers, or special test runners. Demonstrating that `main.go` remains untouched builds instant credibility.

### 2. Gotcha: Graceful Application Shutdown
When testing Go applications built with `go build -cover`, Go writes its coverage profile upon receiving a termination signal (`SIGTERM` / `SIGINT`). If your Go app exits abruptly without catching signals, coverage profiles can be lost or corrupted.
```go
// Recommended pattern in main.go
quit := make(chan os.Signal, 1)
signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
<-quit
log.Println("Shutting down server gracefully...")
```

### 3. Gotcha: Delay Flag (`--delay`)
When running containerized applications, the application container requires a few seconds to boot and establish listener sockets on port `8080`. Always use `--delay 10` (or appropriate seconds) so Keploy doesn't start replaying requests before the server is ready to accept traffic.

### 4. CI/CD Pipeline Superpower
In GitHub Actions, you can run `keploy test` as a lightweight step without needing service containers for MongoDB, Postgres, or Redis. Test execution times drop from minutes to seconds, eliminating cloud infrastructure costs and flaky test runs.
